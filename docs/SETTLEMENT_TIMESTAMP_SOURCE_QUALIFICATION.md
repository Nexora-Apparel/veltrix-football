# Settlement Timestamp Source Qualification Adapter

## Purpose

The 5DollarFootballAPI and StrikerAPI fixture payloads currently prove terminal
match status but do not document a wall-clock full-time timestamp. The adapter
in `app/settlement_timestamp_source.py` accepts timestamps only from a
separately qualified source. It does not infer settlement time from kickoff,
match duration, event minutes, odds ticks, provider update time, or retrieval.

## Admission boundary

The adapter requires a source contract with:

- an exact source identifier;
- `qualification_status: qualified`;
- a 64-character qualification digest referring to the independently
  verified qualification record;
- an explicit timestamp field path;
- timestamp semantics exactly `final_whistle`;
- an explicit list of supported competition IDs.

The contract is a consumer of a separately verified qualification registry.
The acquisition dataset bridge now verifies the registry signature and
resolves the exact source contract before admitting evidence. A digest provides
integrity, not proof of source authenticity or factual truth.

## Evidence contract

Each candidate binds:

- exact source fixture ID, competition, home/away canonical team IDs and kickoff;
- exact expected fixture identity (no fuzzy name or score-based matching);
- raw source payload and canonical SHA-256;
- timestamp field and declared semantics;
- settlement timestamp with explicit timezone;
- observation and retrieval timestamps, ordered after settlement;
- source qualification digest and a canonical evidence digest.

Naive timestamps, unsupported semantics, unqualified competitions, identity
mismatches, pre-kickoff settlement times, observation/retrieval chronology
violations and tampered evidence are rejected.

## Multi-source reconciliation

When more than one qualified source is available, each source may contribute
one candidate. Duplicate source IDs are rejected. The reconciler rejects
cross-source disagreement greater than the configured tolerance (default 60
seconds). It does not silently average timestamps. Reconciliation output is
still evidence, not automatic dataset admission.

## Current limitation

No real timestamp source has been qualified. The adapter, signed registry and
provider dataset bridge integration currently have synthetic contract tests
only. Existing 5Dollar and StrikerAPI records remain ineligible for training
labels until a real source is qualified, its evidence is integrated, and
historical feature availability is independently proven. No model training,
production import, prediction publication or Telegram delivery is enabled.

## Acquisition bridge integration — 2026-11-10

The provider acquisition dataset bridge now accepts an explicit
`settlement_timestamp_package` for each provider fixture. The package binds
the independently qualified source contract, its raw payload, source fixture
identity, reviewed expected fixture identity, and the evidence generated by
`app/settlement_timestamp_source.py`.

The bridge separately verifies the provider's terminal-status evidence and
the external final-whistle evidence. It rejects missing packages, unqualified
contracts, unsupported timestamp semantics, fixture identity mismatches,
payload/evidence tampering, and provider result retrieval earlier than the
external settlement timestamp. It carries the qualification digest and
settlement-evidence digest into the acquisition source manifest.

This integration does **not** qualify a provider or prove historical result
availability at a past prediction cutoff. The bridge now verifies the signed
qualification registry against a runtime KMS-client allowlist built from
out-of-band ARN-to-region configuration. It also requires an audited
cross-provider fixture mapping bound to the acquired provider record. The
existing point-in-time feature builder continues to require source
retrieval/availability before each historical feature cutoff. Retrospectively
downloading a finished match today does not make it eligible for a historical
backtest.

The bridge remains offline and side-effect-free. No external timestamp source
has been qualified, no archive has been acquired, and no model training or
publication is enabled by this integration.

## Signed source qualification registry — 2026-11-10

`app/source_qualification_registry.py` now implements a versioned KMS-signed
registry. A registry is trusted only when its ECDSA-SHA256 signature verifies
against an explicitly supplied out-of-band ARN-to-KMS-client allowlist.
The key ARN inside the registry signature is only a lookup key into that
allowlist; it cannot introduce a new trust anchor.

Each source entry binds a qualification record, its canonical SHA-256,
competition scope, timestamp field and final-whistle semantics, qualification
evidence digests, validity interval and optional revocation time. Resolution
recomputes the qualification-record digest and rejects modified records,
unsupported semantics, duplicate source IDs, expired registries, inactive or
revoked sources, and unsupported competitions.

The provider acquisition dataset bridge now requires the signed registry in
each settlement package, while trusted KMS clients are injected separately
from the evidence package as a runtime trust dependency. Production callers
must construct that mapping only from out-of-band configuration; an archive
or acquisition payload cannot add trusted keys. The bridge resolves the source
at the provider record's retrieval timestamp and requires the supplied
contract to equal the registry-resolved contract before accepting timestamp
evidence. The output manifest retains the registry digest and signing-key
ARN alongside the qualification and timestamp-evidence digests.

This is a cryptographic trust and software-enforcement boundary, not proof
that a source's timestamp is factually correct. Qualification evidence still
requires human/source review, and the real KMS key, registry publication,
external timestamp source and competition coverage have not been configured
or verified. CI uses a deterministic fake KMS implementation only. No live
acquisition, training, prediction publication or Telegram delivery is enabled.

## Additional fail-closed controls — 2026-11-10

The signed registry now rejects unknown top-level fields and unknown signature
envelope fields, preventing unsigned extension data from being mistaken for
part of the versioned contract. A source cannot become active before its
qualification timestamp. The provider bridge also binds the reviewed expected
fixture identity back to the acquired record's competition, canonical home
and away team IDs, and kickoff timestamp. This prevents a valid external
timestamp for one fixture from being attached to a different provider result
through a mismatched crosswalk.

Regression coverage includes tampered and untrusted registries, inactive or
revoked sources, unsupported competitions, source activation chronology,
provider-to-external fixture mismatch, missing settlement timestamps and
provider retrieval chronology. These tests use fake KMS signatures and
synthetic fixtures; they do not qualify a real provider or establish model
training eligibility.

Registry issuance now also requires the signing key to be present in an
out-of-band ARN-to-region signing allowlist. A caller cannot ask the signing
helper to create a registry under an arbitrary KMS key and treat that action
as trusted issuance. Verification and signing use separate explicit trust
inputs, and both fail closed on unknown keys or region mismatches.


## Genius Sports public-documentation review — 2026-11-11

**Decision: candidate only; not qualified, not activated, and no spend or vendor request has been made.**

### Timestamp semantics

The public LiveStats Football TV Feed documentation defines a `summary`
message that is usually sent once at the end of a match. It exposes
`timeEndActual` as the actual match end time in UTC. This is a materially
stronger candidate than a generic `Finished` status.

However, the same documentation describes this TV Feed as a TCP socket
connection to the LiveStats software running at the venue (default port
7677, configurable by the venue statistician). It does not establish that
historical summary messages can be retrieved from a cloud archive or that
the feed is available to a remote non-venue consumer. Therefore the field
semantics are documented, but practical historical availability and licensed
access are not.

The Warehouse Football REST API documents historical and future match,
player, team-statistics and match-action retrieval. Its public reference does
not document a `timeEndActual` field or a timestamp contract for a
`game/end` action. The existence of a `game/end` action type is not enough
to qualify its event timestamp as final-whistle time. Do not substitute
`eventStatusType=Finished`: Fixtures API v2 explicitly warns that this status
is not set at the exact end and may take up to an hour to update.

### Access, licensing and historical coverage

- Warehouse REST API calls require an `x-api-key`; the key defines access
  permissions and quota. The public response contract includes unauthorized
  and not-authorized outcomes.
- Fixtures API v2 requires an Auth0 client ID/secret and an API key supplied
  by Genius Sports; the documentation directs customers to their integration
  manager.
- Genius Sports states that production exposes the content the customer is
  licensed for; UAT may not expose all licensed content.
- Public documentation does not establish a price, the user's eligibility,
  the exact competitions covered by a prospective account, historical
  `timeEndActual` archive retention, revision/correction semantics, or
  rights to retain and use the data for model training/backtesting.

### Potential feature domains (not yet qualified)

Fixtures API v2 documents rosters and says fixture-specific lineups are
supported only for Football and a limited number of competitions. The
Warehouse Football REST API documents injury endpoints and match/team/person
statistics. This suggests possible future injury, lineup and match-statistics
coverage, but does not prove competition coverage, pre-kickoff availability,
field completeness, or licensing for VELTRIX. The reviewed public reference
does not explicitly establish xG or PPDA fields. Those must remain absent
until a licensed field-level schema and timestamp semantics are confirmed.

### Required vendor answers before any qualification

1. Can the LiveStats `summary.timeEndActual` be retrieved historically for
   completed football matches, including exact competition and season IDs?
2. Is the TV Feed available outside venue-local TCP access, or is there a
   licensed warehouse endpoint exposing the same immutable timestamp?
3. Are `timeEndActual` values corrected or revised after publication? How
   are abandoned, postponed, replayed, extra-time and penalty matches handled?
4. What are historical retention, pagination, rate limits, correction logs,
   and source-side observation/publication timestamps?
5. Which competitions, seasons, women's/reserve/youth scopes, injury records,
   lineups and statistics are licensed to the customer?
6. What are the permitted retention, storage, derived-feature, backtesting,
   model-training and redistribution rights, and the commercial price?

Until those questions are answered with written documentation and a
competition-level sample, Genius Sports is **not** a qualified settlement
source. No timestamp may enter the signed settlement registry. No KMS
qualification, credentials, API requests, credits or purchase are authorized
by this research.
